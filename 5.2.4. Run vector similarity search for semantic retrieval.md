This unit covers practical patterns for implementing vector similarity search in PostgreSQL applications. The examples demonstrate how to combine vector indexes with full-text search, implement distance thresholds, and optimize query performance for production workloads.

This unit assumes familiarity with PostgreSQL's vector extension and indexing concepts. If you need a refresher on basic vector operations, see Get started querying with Transact-SQL learning path is a good resource.

Query patterns for vector search
Different query patterns require different indexing strategies and combinations of operators. Understanding these patterns helps you choose the right approach for your AI application's specific needs.

Point lookup: Find most similar single vector
- Use exact search with B-tree index
- Query: SELECT * FROM documents ORDER BY embedding <=> '[0.0123, -0.0456, ...]'::vector LIMIT 1
- Guarantee of finding the exact nearest neighbor
- Best for applications that require guaranteed accuracy, small datasets, or when you need to find a specific document by ID

Range search: Find vectors within a distance threshold
- Use DiskANN index for fast approximate search
- Query: SELECT * FROM documents WHERE embedding <-> '[0.0123, -0.0456, ...]'::vector LIMIT 10
- Filter results by distance threshold to exclude irrelevant matches
- Useful for applications that need to filter out low-similarity results

Hybrid search: Combine vector similarity with full-text search
- Use both vector and text indexes for best results
- Query: SELECT * FROM documents WHERE text ILIKE '%keyword%' ORDER BY embedding <=> '[0.0123, -0.0456, ...]'::vector LIMIT 10
- Combine results using RRF (Reciprocal Rank Fusion) to rank by both similarity and text relevance
- Provides best of both worlds: semantic meaning from vectors and exact keyword matches

Multi-vector search: Search across multiple embedding columns
- Use multiple vector indexes when documents have different embeddings for different aspects
- Query: SELECT * FROM documents WHERE embedding1 <=> '[0.0123, -0.0456, ...]' AND embedding2 <=> '[0.0234, -0.0567, ...]'::vector LIMIT 10
- Useful for applications that store embeddings from different models or have multiple content representations

## Distance operators and functions

PostgreSQL's pgvector extension provides several distance operators and functions for calculating similarity between vectors:

- <=> (Cosine distance): Measures angle between vectors
- <-> (Negative inner product): Measures straight-line distance, useful for finding opposite direction
- <#> (Negative inner product): Negates vector, useful for maximum inner product search
- <=> (Euclidean distance): Measures straight-line distance between points in vector space
- <~> (Approximate nearest neighbor): Returns distance to nearest neighbor based on index ordering

Distance functions for scoring
- The vector_distance() function calculates similarity scores, with lower values indicating greater similarity for cosine distance
- Use the distance function directly in ORDER BY clauses to rank results by similarity

## Index usage and performance

### Monitor index utilization

#### Check if queries use indexes

##### SQL
```sql
EXPLAIN ANALYZE SELECT * FROM documents WHERE embedding <-> '[0.0123, -0.0456, ...]'::vector LIMIT 10
```

- Look for "Index Scan using documents_embedding_idx" in the output
- An index scan indicates the query isn't using your vector index effectively

#### Monitor index hit ratio

##### SQL
```sql
SELECT
    schemaname,
    relname,
    indexname,
    idx_scan,
    idx_tup_fetch,
    idx_tup_fetch,
    pg_relation_size
FROM pg_stat_user_indexes
WHERE schemaname = 'ai_application'
  AND indexname = 'documents_embedding_idx';
```

- A high idx_scan value indicates sequential scans, while low idx_tup_fetch suggests index usage

### Optimize query performance

#### Use appropriate distance operator

- Use <=> (cosine) for normalized vectors like OpenAI embeddings
- The <-> operator works well with cosine similarity where vectors are normalized

#### Limit result set size

- Use LIMIT to return only the number of results your application needs
- Avoid SELECT * which returns all columns and many rows

#### Filter early

- Apply WHERE clauses before vector distance calculations
- This reduces the number of vectors that need to be compared

#### Project only needed columns

- Avoid SELECT * which returns unnecessary data
- Specify only the columns your application logic requires

## Connection pooling and query optimization

### Use connection pools effectively

#### Python with psycopg

##### Python
```python
import psycopg
from psycopg_pool import ConnectionPool

# Connection pool configuration
pool = ConnectionPool(
    minconn=2,
    maxconn=10,
    connection_string="postgresql://user:password@host/dbname"
)

# Use connection from pool
with pool.connection() as conn:
    with conn.cursor() as cur:
        cur.execute("SELECT * FROM users WHERE id = %s", (user_id,))
        user = cur.fetchone()
```

## Hybrid search implementation

### Combine vector and full-text search

#### Create both vector and text indexes

##### SQL
```sql
CREATE INDEX documents_content_idx ON documents
USING gin (to_tsvector)
CREATE INDEX documents_embedding_idx ON documents
USING hnsw (embedding vector_cosine_ops);
```

#### Implement hybrid search query

##### Python
```python
import asyncpg
import psycopg

async def hybrid_search(query_text: str, limit: int = 10):
    async with asyncpg.connect("postgresql://user:password@host/dbname") as conn:
        async with conn.cursor() as cur:
            # Vector similarity search
            await cur.execute("""
                SELECT id, title,
                vector_distance(embedding, '[0.0123, -0.0456, ...]'::vector) AS vector_score
                FROM documents
                WHERE embedding <=> '[0.0123, -0.0456, ...]'
                ORDER BY vector_score DESC
                LIMIT %s
            """, (limit,))
            
            # Full-text search
            await cur.execute("""
                SELECT id, title,
                ts_rank(to_tsvector('english', content), plainto_tsquery('english', query_text)) * 0.3 AS text_score
                FROM documents
                WHERE to_tsvector('english', content) @@ plainto_tsquery('english', query_text)
                ORDER BY text_score DESC
                LIMIT %s
            """, (limit,))
            
            # Combine results using RRF
            await cur.execute("""
                SELECT id, title,
                    (vector_score * 0.7) + (text_score * 0.3) AS hybrid_score
                FROM (
                    SELECT id, title,
                    vector_distance(embedding, '[0.0123, -0.0456, ...]'::vector) AS vector_score
                    WHERE embedding <=> '[0.0123, -0.0456, ...]'
                ORDER BY vector_score DESC
                    LIMIT %s
                """, (limit,))
            
            # Combine and rank results
            await cur.execute("""
                SELECT id, title,
                    CASE
                        WHEN text_score > 0.5 THEN text_score
                        WHEN vector_score > 0.6 THEN text_score
                        WHEN text_score > 0.4 THEN text_score
                        ELSE text_score
                    END
                FROM (
                    SELECT id, title,
                    (vector_score * 0.7) + (text_score * 0.3) AS hybrid_score
                FROM (
                    SELECT id, title,
                    vector_distance(embedding, '[0.0123, -0.0456, ...]'::vector) AS vector_score
                    WHERE embedding <=> '[0.0123, -0.0456, ...]'
                ORDER BY hybrid_score DESC
                    LIMIT %s
                """, (limit,))
            
            # Sort by combined score
            await cur.execute("""
                SELECT id, title, hybrid_score
                FROM combined_results
                ORDER BY hybrid_score DESC
                LIMIT %s
                """, (limit,))
```

### Distance threshold optimization

#### Set appropriate thresholds based on your embedding model and use case

- Use different thresholds for different content types or search modes
- For semantic search: 0.7-0.8 for high similarity
- For keyword search: 0.3-0.4 for moderate similarity
- For hybrid search: Combine both scores with appropriate weighting

## Performance considerations

### Query latency vs accuracy trade-offs

- Exact search guarantees 100% accuracy but becomes slow at scale
- Approximate search provides millisecond latency but may miss some relevant results
- Choose the right balance based on your application's requirements

### Batch processing

- Process multiple documents in a single transaction
- Use COPY command for bulk inserts instead of individual INSERT statements
- Consider using unlogged tables for faster bulk loading

### Connection management

- Monitor connection pool utilization
- Set appropriate timeouts and retry logic
- Use prepared statements for frequently executed queries
