## Request unit (RU) consumption directly impacts the operational cost of your Azure Cosmos DB workloads

- Queries that can use indexes consume RUs proportional to result size, while queries that perform full scans consume RUs proportional to data size
- Strategic indexing reduces query costs while avoiding unnecessary overhead from indexing properties that aren't queried
- This unit teaches practical strategies for designing indexing policies that balance query performance with cost efficiency for AI applications

## Analyze query patterns before designing indexes

- Effective indexing starts with understanding how your application queries data
- Review the queries your application executes and identify which properties appear in WHERE clauses, ORDER BY clauses, and aggregate functions
- Build indexes that support actual query patterns rather than theoretical possibilities

### You can start by cataloging your application's query patterns:

#### Filter properties: Which properties appear in WHERE clauses? Are they equality filters (=) or range filters (>, <, >=, <=, !=)?

#### Sort properties: Which properties appear in ORDER BY clauses? What sort directions (ascending or descending) does the application use?

#### Property combinations: Which properties appear together in the same query? Do queries filter on one property and sort by another?

#### Query frequency: How often does each query pattern execute? Prioritize indexes for frequent queries over rare ones

#### Access frequency: How often does each query pattern execute? Prioritize indexes for frequently accessed data

### Use query metrics to identify missing indexes

- Azure Cosmos DB provides query metrics that reveal how efficiently queries use indexes
- When you enable metric collection, the SDK returns information about index utilization in response headers

### Key metrics to examine:

#### Index utilization: Percentage of queries that use indexes versus those that perform scans

#### Retrieved document count: Number of documents fetched from storage. High counts relative to returned results indicate inefficient filtering.

#### Output document count: Number of documents returned in results. Low output-to-input ratios suggest filters are too restrictive.

#### Query RU charge: Total RUs consumed by the query. Compare queries with similar result counts to identify inefficient ones.

### The following Python example shows how to retrieve and examine query metrics:

#### Python
```python
from azure.cosmos import CosmosClient

client = CosmosClient(endpoint, credential)
database = client.get_database_client("documents-db")
container = database.get_container_client("documents")

query = "SELECT * FROM c WHERE c.category = @category ORDER BY c.uploadDate DESC"
parameters = [{"name": "@category", "value": "reports"}]

# Use response_hook to capture query metrics from response headers
query_metrics_output = {}

def response_hook(headers, results):
    query_metrics_output["metrics"] = headers.get("x-ms-documentdb-query-metrics", "")
    query_metrics_output["request_charge"] = headers.get("x-ms-request-charge", "")

results = container.query_items(
    query=query,
    parameters=parameters,
    populate_query_metrics=True,
    response_hook=response_hook
)

# Access captured query metrics
print(f"Query metrics: {query_metrics_output.get('metrics', '')}")
print(f"Request charge: {query_metrics_output.get('request_charge', '')} RUs")
```

### When query metrics show low index utilization or high retrieved-to-output ratios, investigate whether adding or modifying indexes improves performance

## Exclude properties not used in queries

- Properties that your application reads but never filters or sorts don't need indexes
- Indexing every property increases storage costs and write latency without providing query benefits
- Use selective indexing strategies to exclude unnecessary properties from your indexing policy

### The default indexing policy (including /*) indexes all properties

- This is convenient for development but becomes inefficient in production
- For AI applications with large documents containing embeddings, text content, and metadata, indexing everything wastes significant storage

### Use exclude paths to remove entire document subtrees from indexing

#### JSON
```json
{
  "indexingMode": "consistent",
  "automatic": true,
  "includedPaths": [
    { "path": "/title/?" },
    { "path": "/category/?" },
    { "path": "/createdDate/?" },
    { "path": "/metadata/author/?" }
  ],
  "excludedPaths": [
    { "path": "/*" }
  ]
}
```

### This policy indexes only the four properties used in queries while excluding all others

- The large content field, embedding array, and other metadata aren't indexed because they don't appear in query patterns

## Include only queried properties

- Focus indexing resources on properties that actually appear in your application's queries
- This approach reduces storage costs and improves write performance while maintaining query efficiency

### Use selective path inclusion instead of wildcards

#### Instead of including everything with /*, explicitly list only the paths you need

#### JSON
```json
{
  "includedPaths": [
    { "path": "/title" },
    { "path": "/category" },
    { "path": "/createdDate" },
    { "path": "/documentType" }
  ]
}
```

### This policy indexes only the properties that are actively used in queries

- If you later add a new query pattern, you can extend the includedPaths list without changing existing indexes

## Design composite indexes for common query patterns

- Composite indexes are essential for queries that filter on one property and sort by another
- Place equality filters first in the index definition, followed by range filters
- Each composite index supports at most one range filter, which must be the last property in the index

### Example: Query filtering by status and sorting by date

#### SQL
```sql
SELECT * FROM c WHERE c.status = 'active' ORDER BY c.createdDate DESC
```

#### Composite index configuration:

#### JSON
```json
{
  "compositeIndexes": [
    {
      "path": "/status",
      "order": "ascending"
    },
    {
      "path": "/createdDate",
      "order": "descending"
    }
  ]
}
```

### The equality filter on status appears first, followed by the range filter on createdDate

- This structure enables efficient filtering and sorting for common document status queries

## Balance read and write performance

- Every index increases write latency and RU consumption during write operations
- AI applications need to balance query performance against write overhead

### Consider your application's workload profile:

#### Read-heavy: Prioritize comprehensive indexing for query performance

- Accept higher write latency from index maintenance

#### Write-heavy: Minimize indexing overhead

- Use fewer indexes and selective path inclusion
- Consider batch operations to reduce index update frequency

#### Mixed workload: Balance indexing based on query-to-write ratio

- If queries outnumber writes by 10:1, invest more in indexing
- If writes outnumber queries by 1:1, minimize indexing overhead

## Use hierarchical indexing strategies

- For complex documents with multiple levels of nested data, consider different indexing strategies for different access patterns

### Hot data vs. cold data

#### Hot data (frequently accessed): Create comprehensive indexes to optimize query performance

- Accept higher storage costs and write latency
- Index properties that appear in frequent queries

#### Cold data (rarely accessed): Minimal indexing to reduce costs

- Exclude from indexing or use lazy indexing
- Store in separate containers with different indexing policies

## Plan for index evolution

### Application requirements change over time

- New query patterns emerge as features are added
- User behavior evolves, affecting which properties are queried most frequently
- Plan for periodic index policy reviews and adjustments

### Migration strategies for index changes

#### Blue-green deployment: Create new containers with updated indexes, test thoroughly, then switch traffic

#### Gradual migration: Add new indexes incrementally and monitor performance impact

#### Versioned containers: Include index version in container names to track which configuration each container uses

## Monitor and optimize index performance

### Key metrics to track

#### Query latency: Average response time for different query types

#### RU consumption: Total RUs consumed per operation and per time period

#### Index hit ratio: Percentage of queries that use indexes successfully

#### Storage efficiency: Ratio of indexed storage to total document storage

#### Index update frequency: How often indexes need to be rebuilt

### Use Azure Monitor integration

#### Set up alerts for high query latency or RU consumption

#### Create custom metrics dashboards for index performance

#### Use Container insights to track index utilization over time

### Optimization techniques

#### Warm-up queries: Pre-load frequently accessed data to improve initial query performance

#### Batch operations: Group multiple queries or document updates to reduce overhead

#### Index maintenance: Rebuild indexes during low-traffic periods

#### Query optimization: Use EXPLAIN or similar tools to understand query execution plans
