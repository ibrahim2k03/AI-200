## Understand vector index types

- Azure Cosmos DB offers three vector index types, each optimized for different dataset sizes and accuracy requirements
- Understanding the trade-offs helps you select the right type for your AI application

### Flat index for small datasets

#### The flat index performs brute-force k-nearest neighbor search, comparing the query vector against every indexed vector

- This approach guarantees 100% accuracy because it evaluates all vectors without approximation
- Limitations:
  - Maximum of 505 dimensions per vector
  - Higher latency and RU consumption for large datasets because every vector is compared
  - No support for approximate search optimizations

#### When to use flat indexes:

##### Small datasets where the vector count per physical partition is modest

##### Scenarios where flat indexes work well:

- Applications requiring guaranteed accuracy where approximate results aren't acceptable
- Development and testing environments with small datasets
- Workloads where query patterns are unpredictable and you need exact results
- Applications where the vector count per partition is less than a few thousand

##### Limitations to consider:

- Performance degrades linearly as dataset size increases
- Storage costs are higher than other index types due to lack of compression
- Not suitable for real-time applications with large datasets

### QuantizedFlat index for medium datasets

#### The quantizedFlat index compresses vectors using quantization before storing them in the index

- This approach still performs brute-force search but with reduced latency and RU cost
- Key characteristics:
  - Supports up to 4,096 dimensions
  - Reduces storage requirements by 50% compared to float32
  - Maintains high accuracy while improving throughput
  - Uses 8-bit quantization (int8) by default

#### When to use quantizedFlat indexes:

##### Medium datasets with roughly 1,000 to 50,000 vectors per physical partition

##### Scenarios where quantizedFlat indexes work well:

- Production applications with moderate dataset sizes where accuracy is important but storage costs are a concern
- Applications where you need better performance than flat indexes but can't tolerate the slight accuracy reduction from quantization
- Workloads where query latency is critical and you need to optimize throughput

##### Quantization considerations:

- Most models show minimal accuracy loss with 8-bit quantization for text embeddings
- Test quantization impact on your specific model and use case before production deployment
- Consider 16-bit quantization (float16) if 8-bit causes unacceptable accuracy loss

### DiskANN index for large datasets

#### The diskANN index uses Microsoft Research's DiskANN algorithm for fast approximate nearest neighbor search

- This approach provides the best performance for large datasets while maintaining high accuracy
- Key characteristics:
  - Supports up to 4,096 dimensions
  - Uses specialized data structures optimized for vector similarity search
  - Maintains high recall while dramatically reducing query costs
  - Scales efficiently to millions of vectors per partition

#### When to use diskANN indexes:

##### Large datasets with more than 50,000 vectors per physical partition

##### Scenarios where diskANN indexes work well:

- Production AI applications with large embedding collections
- Semantic search platforms where query latency is critical
- Applications where RU efficiency is more important than exact accuracy
- Workloads where approximate results are indistinguishable from exact results in practice

##### Performance characteristics:

- Query latency measured in milliseconds rather than seconds
- RU consumption scales with log(N) rather than linear with dataset size
- High throughput (thousands of queries per second) with consistent performance

##### DiskANN parameters to consider:

- indexingSearchListSize: Controls how many vectors are evaluated during index construction (default: 100, valid: 10-500)
- Higher values improve index quality at the cost of longer index build times
- quantizationByteSize: Controls vector compression (default: 64 bytes, valid: 8-512 bytes)
- Larger values preserve more information but increase index size and build time

## Select the right vector index type

### Evaluate your application requirements

#### Dataset size: Small (<1,000 vectors/partition), Medium (1,000-50,000), or Large (>50,000 vectors/partition)

#### Accuracy requirements: Guaranteed (no approximation), High (minimal approximation tolerance), or Standard (some approximation acceptable)

#### Performance priorities: Lowest latency, Highest throughput, or Balanced cost and performance

#### Query patterns: Point lookups (single vector), Range queries (filtered similarity), or Hybrid search (combined vector and metadata)

### Decision matrix for vector index selection

| Dataset Size | Accuracy Required | Performance Priority | Recommended Index Type |
|---|---|---|---|---|
| Small | Any | Lowest latency | Flat |
| Small | High | Highest throughput | QuantizedFlat |
| Medium | High | Balanced cost and performance | QuantizedFlat |
| Large | Standard | Highest throughput | DiskANN |

### Use this matrix as a starting point for your selection

- Consider your current dataset size and growth projections
- If you expect to grow from small to medium, start with QuantizedFlat and plan to migrate to DiskANN as you approach 50,000 vectors per partition
- For applications already at large scale, DiskANN provides the best performance characteristics

## Integrate vector indexes with other index types

### Vector indexes work alongside range, composite, and spatial indexes within the same indexing policy

- This enables comprehensive query patterns that combine semantic search with traditional filtering and geospatial operations
- The indexing policy must include all necessary index types to support your complete application functionality

### Example comprehensive indexing policy for an AI knowledge base:

#### JSON
```json
{
  "indexingMode": "consistent",
  "automatic": true,
  "includedPaths": [
    { "path": "/*" }
  ],
  "excludedPaths": [
    { "path": "/\"_etag\"/?" },
    { "path": "/embedding/*" }
  ],
  "compositeIndexes": [
    {
      "path": "/category",
      "order": "ascending"
    },
    {
      "path": "/createdDate",
      "order": "descending"
    }
  ],
  "vectorIndexes": [
    {
      "path": "/embedding",
      "type": "diskANN",
      "quantizationByteSize": 64,
      "indexingSearchListSize": 200
    }
  ],
  "spatialIndexes": [
    {
      "path": "/location",
      "type": "point"
    }
  ]
}
```

### This policy demonstrates a production-ready configuration:

- Range indexes on category and createdDate for filtering and sorting
- Composite index on category and createdDate for metadata-based sorting
- DiskANN vector index for high-performance semantic search
- Spatial index on location for geographic queries
- Selective path inclusion to exclude unnecessary properties from indexing

## Plan for vector index immutability

### Vector policies can't be modified after container creation

- Once you create a container with a vector policy, the embedding properties and distance function are fixed
- Changing vector index types requires creating a new container and migrating data
- Plan your vector index strategy carefully during application design

### Migration strategies:

#### Blue-green deployment: Create new container with updated vector index, test thoroughly, then switch traffic

#### Gradual migration: If you need to change index types, create new containers alongside existing ones and migrate data incrementally

#### Versioned containers: Include index version in container name to track which vector index configuration each container uses

## Monitor and optimize vector index performance

### Key metrics to track

#### Query latency: Measure average response time for vector similarity queries

#### RU consumption: Track request units consumed by vector queries

#### Index size: Monitor storage used by vector indexes

#### Recall and accuracy: Periodically test query quality to ensure index effectiveness

### Optimization techniques

#### Warm-up queries: Pre-load frequently accessed vectors into cache to improve initial query performance

#### Batch operations: Group multiple vector queries or document updates to reduce overhead

#### Index maintenance: Rebuild indexes during low-traffic periods when changing configurations

### Azure Monitor integration

#### Set up alerts for high query latency or RU consumption

#### Use Container insights to track vector index performance metrics

#### Create custom metrics dashboard for vector query patterns
