# 5.2.2. Perform fast vector similarity search

As your vector dataset grows, similarity queries that scan every row become too slow for production use. Vector indexes enable PostgreSQL to find relevant vectors through efficient nearest neighbor search rather than scanning entire tables. This unit covers indexing strategies, query patterns, and performance optimization techniques for building scalable vector search applications.

This unit assumes familiarity with standard SQL concepts like SELECT, WHERE, joins, and aggregation. If you need a refresher, see Get started querying with Transact-SQL learning path is a good resource.

Indexing strategies for vector search
PostgreSQL provides three vector index types that optimize for different dataset sizes and accuracy requirements. Understanding the trade-offs helps you select the right approach for your AI application.

Exact search with B-tree indexes
B-tree indexes perform exact nearest-neighbor search, comparing your query vector against every indexed vector. This approach guarantees 100% recall but becomes increasingly slow as dataset size grows. For small tables (under 10,000 rows) or when you need guaranteed accuracy, exact search provides the best user experience.

Approximate search with specialized indexes
IVFFlat and DiskANN indexes use approximate nearest neighbor algorithms to dramatically improve query performance at scale. These approaches trade perfect accuracy for significantly faster search, which is often acceptable for AI applications where approximate results are indistinguishable from exact ones.

DiskANN indexes provide the best performance for large datasets
DiskANN uses Microsoft Research's DiskANN algorithm to organize vectors into data structures optimized for similarity search. This approach maintains high recall while reducing query costs from linear to logarithmic scaling with dataset size. For tables with millions of vectors, DiskANN can reduce query latency from seconds to milliseconds.

HNSW indexes for hierarchical data
HNSW (Hierarchical Navigable Small World) indexes organize vectors into a multi-layer graph structure. This approach works well for data with inherent hierarchies, such as product categories or document sections. The algorithm enables efficient coarse-to-fine search, starting at top layers and narrowing down to specific items.

Choosing the right index type
Select based on your dataset size and accuracy requirements:

- Small datasets (<10,000 vectors): Use exact search with B-tree indexes
- Medium datasets (10,000-50,000 vectors): Use IVFFlat for good balance of speed and accuracy
- Large datasets (>50,000 vectors): Use DiskANN for best performance at scale

Index configuration parameters
DiskANN indexes accept several parameters that control their behavior:

#### indexingSearchListSize: Number of vectors to evaluate during index construction (default: 100, range: 10-500)
- Higher values improve index quality but increase build time and storage

#### quantizationByteSize: Controls how many bytes per vector dimension (default: 64, range: 8-512)
- Larger values preserve more information but increase index size and memory usage

#### ef_construction: Index building parameters (default: 64, range: 8-1024)
- Controls memory usage during index construction (higher values use more RAM but build better indexes)

Query patterns for vector search
Different query patterns require different indexing strategies:

Point lookup: Find most similar single vector
- Use exact search with B-tree index
- Query: SELECT * FROM documents ORDER BY embedding <=> '[0.0123, -0.0456, ...]'::vector LIMIT 1

Range search: Find vectors within a distance threshold
- Use DiskANN index for fast approximate search
- Query: SELECT * FROM documents WHERE embedding <-> '[0.0123, -0.0456, ...]'::vector LIMIT 10
- Filter results by distance threshold to exclude irrelevant matches

Hybrid search: Combine vector similarity with full-text search
- Use both vector and text indexes for best results
- Query: SELECT * FROM documents WHERE text ILIKE '%keyword%' ORDER BY embedding <=> '[0.0123, -0.0456, ...]'::vector LIMIT 10
- Combine results using RRF (Reciprocal Rank Fusion) to rank by both similarity and text relevance

Index maintenance and monitoring
Vector indexes require maintenance as data changes

- Monitor index statistics and query performance metrics
- Rebuild indexes during low-traffic periods to incorporate new data
- Consider automatic vacuuming to maintain index efficiency
- Use PARTITION BY range for large tables to keep indexes small and efficient

## Performance optimization techniques

### Query optimization

#### Use appropriate distance operator

- Use <-> (cosine) for normalized vectors like OpenAI embeddings
- Use <=> (inner_product) for dot product when vectors are normalized
- Distance metrics help you choose the right operator for your embedding model

#### Limit result set size

- Use LIMIT to return only the number of results your application needs
- Implement pagination for large result sets
- Consider keyset pagination for better performance with large datasets

#### Filter early

- Apply WHERE clauses before vector distance calculations
- This reduces the number of vectors that need to be compared
- Use selective indexes to enable efficient pre-filtering

#### Project only needed columns

- Avoid SELECT * which returns all columns
- Specify only the columns you need for your application logic

### Connection pooling

#### Use connection pools to reduce overhead

- Reuse connections across multiple queries
- Configure appropriate pool size based on your application's concurrency
- Use context managers to ensure proper connection cleanup
