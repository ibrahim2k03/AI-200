Retrieval-augmented generation (RAG) combines vector similarity search with large language model (LLM) context to provide accurate, grounded answers to user queries. This unit covers practical patterns for implementing RAG systems in PostgreSQL, from document ingestion to response generation.

Understanding RAG architecture
RAG systems typically follow this workflow:

- Document ingestion: Store raw documents in PostgreSQL with metadata and embeddings
- Embedding generation: Convert documents to vector representations using embedding models like OpenAI
- Vector storage: Store embeddings alongside documents using pgvector extension
- Retrieval: When user queries arrive, convert query to vector and search for similar documents
- Response generation: Retrieve relevant documents and pass both retrieved content and original query to LLM
- Augmentation: Enhance retrieved documents with additional context before generating responses

This architecture enables your AI application to answer questions based on its own knowledge base while incorporating current information, improving accuracy and user trust.

Document ingestion strategies
Store documents with clear metadata for filtering and retrieval
Use separate tables for different document types (contracts, policies, user data)
- Include document type, category, creation date, and status
- Store raw content alongside structured metadata for flexibility
- Add timestamps for tracking document lifecycle and freshness
- Use JSONB columns for semi-structured metadata that can be queried and indexed

Embedding generation and storage
Generate embeddings using your chosen embedding model
Choose an appropriate model based on your requirements:
- OpenAI text-embedding-ada-002: 1,536 dimensions, good balance of performance and cost
- OpenAI text-embedding-3-large: 3,072 dimensions, higher accuracy for complex queries
- Local models: For sensitive data or specific domains, consider self-hosted models

Batch processing for efficiency
- Generate embeddings in batches to reduce API calls and costs
- Use parameterized queries to pass multiple documents to embedding API
- Store embeddings immediately after generation to avoid duplicate API calls

Store embeddings with metadata
- Include model version, generation timestamp, and token usage
- Track embedding generation costs and implement caching for frequently used embeddings
- Store vector data type as vector(1536) with appropriate dimensions

Vector indexing for similarity search
Create pgvector indexes optimized for your query patterns
- Use HNSW indexes for large datasets with millions of vectors
- Use IVFFlat indexes for medium datasets with good balance of speed and accuracy
- Configure appropriate parameters (indexingSearchListSize, ef_construction) based on your performance requirements

## Retrieval patterns

### Vector similarity search

#### Basic vector search
Find documents most similar to a query vector using exact nearest neighbor search:

SQL
SELECT id, title, embedding <=> $1 AS distance
FROM documents
ORDER BY embedding <=> $1
LIMIT 10;
This query returns the 10 most similar documents to the query vector, guaranteed to find the exact nearest neighbor.

#### Distance threshold filtering
Add a WHERE clause to exclude results below a similarity threshold:

SQL
SELECT id, title, embedding <=> $1 AS distance
FROM documents
WHERE embedding <=> $1 < 0.8
ORDER BY embedding <=> $1
LIMIT 10;
This query returns documents that are more than 80% similar to the query vector, filtering out less relevant matches.

### Range search

Find documents with vectors within a specified distance from a query vector:

SQL
SELECT id, title, embedding <-> '[0.0123, -0.0456, ...]'::vector
WHERE embedding <-> '[0.0123, -0.0456, ...]'::vector
  AND created_at > '2024-01-01'
ORDER BY created_at DESC
LIMIT 10;
This query finds documents within a distance range from the query vector, sorted by recency.

### Hybrid search

Combine vector similarity with full-text search
Use both vector and text indexes to provide the best results:

SQL
SELECT id, title,
    vector_distance(embedding, '[0.0123, -0.0456, ...]'::vector AS vector_score,
    ts_rank(to_tsvector('english', content), plainto_tsquery('english', $query_text)) * 0.7 AS text_score
FROM documents
WHERE to_tsvector('english', content) @@ plainto_tsquery('english', $query_text)
ORDER BY vector_score DESC, text_score DESC
LIMIT 10;
This query finds documents semantically similar to the query, then ranks them by text relevance within those matches.

Combine results with RRF

SQL
SELECT id, title,
    (vector_score * 0.7) + (text_score * 0.3) AS hybrid_score
FROM (
    SELECT id, title, vector_score, text_score
    FROM (
        SELECT id, title, vector_distance(embedding, '[0.0123, -0.0456, ...]'::vector AS vector_score
        WHERE embedding <=> '[0.0123, -0.0456, ...]'
    ORDER BY vector_score DESC
        LIMIT 10
    )
    CROSS JOIN (
        SELECT id, title, text_score
        FROM (
            SELECT id, title,
                ts_rank(to_tsvector('english', content), plainto_tsquery('english', $query_text)) * 0.3 AS text_score
                FROM documents
                WHERE to_tsvector('english', content) @@ plainto_tsquery('english', $query_text)
                ORDER BY text_score DESC
                LIMIT 10
        )
    )
ORDER BY hybrid_score DESC
LIMIT 10;
This RRF approach combines vector similarity and text relevance, giving priority to semantic matches while still considering text search results.

### Multi-vector search

Search across multiple embedding columns when documents have different content representations:

SQL
SELECT id, title,
    embedding1 <=> '[0.0123, -0.0456, ...]'::vector AS distance1,
    embedding2 <=> '[0.0234, -0.0567, ...]'::vector AS distance2
FROM documents
WHERE embedding1 <=> $1 < 0.8
  AND embedding2 <=> $2 < 0.9
ORDER BY distance1, distance2
LIMIT 10;
This query finds documents where the first embedding is very similar and the second is moderately similar, returning them in order of similarity to the first vector.

#### Format response for LLM

- Pass retrieved documents and original query to LLM
- Include citation metadata to enable LLM to reference sources
- Format results clearly with document titles, content sections, and confidence scores

##### Python
```python
def format_response(documents, query_text: str, results: list):
    response = f"Based on your query: '{query_text}', I found the following relevant information:\n\n"
    
    for doc in results:
        response += f"Document {doc['id']}: {doc['title']}\n"
        response += f"Similarity: {doc['vector_score']:.4f}\n"
        
        if doc.get('text_score', 0) > 0.7:
            response += f"  (High similarity: {doc['title']})\n"
        else:
            response += f" (Moderate similarity: {doc['vector_score']:.4f})\n"
    
    return response
```

### Implement context-aware retrieval

#### Adjust similarity thresholds based on context

##### Python
```python
def adjust_thresholds_by_context(context_docs: list, base_threshold: float = 0.7):
    # Analyze context to determine appropriate thresholds
    # For legal documents, use higher threshold (0.9)
    # For technical documents, use lower threshold (0.5)
    
    # Adjust thresholds based on document type or category
    for doc in context_docs:
        if doc.get('document_type') == 'legal':
            return 0.9
        elif doc.get('category') == 'contracts':
            return 0.6
        else:
            return base_threshold
```
