# 5.1.3. Create and manage schemas

## Database schema design determines how effectively your application stores and retrieves data

- A well-designed schema enforces data integrity through constraints, enables efficient queries through appropriate data types, and supports application evolution through thoughtful structure
- For AI applications that store conversation history, task state, and metadata, schema design choices directly affect both performance and maintainability

## Database and schema organization

- PostgreSQL organizes objects in a hierarchy: a server instance contains databases, databases contain schemas, and schemas contain tables and other objects
- Understanding this hierarchy helps you structure your application's data appropriately and manage permissions effectively

### A server instance can contain multiple databases

- Each database is an isolated container with its own tables, functions, and other objects
- Connections target a specific database, and queries can't directly access objects in other databases on the same server
- This isolation provides security boundaries and enables independent backup and restore strategies for different databases

### Schemas provide namespaces for organizing objects within a database

- Tables and other objects within a schema share the same namespace
- You can create multiple schemas to separate logical components of your application
- For example, use separate schemas for user data, application configuration, and AI model metadata

### The default schema is public

- When you don't specify a schema name in your SQL statements, PostgreSQL uses the public schema
- This is convenient for development but becomes problematic in production with many schemas
- Always specify schema names explicitly in production applications to avoid ambiguity

## Create tables

- Tables store your application's data in rows and columns
- The CREATE TABLE statement defines the table structure, including column names, data types, and constraints

### A table definition specifies each column's name and data type

- Choosing appropriate data types affects storage efficiency and query performance
- PostgreSQL supports a wide range of data types, each optimized for different use cases

#### Common data types for AI applications:

##### BIGSERIAL: Auto-incrementing 64-bit integers for primary keys and large counters

##### UUID: Universally unique identifiers for conversation IDs, session IDs, or task identifiers

##### TEXT: Variable-length character strings for content, messages, or descriptions

##### TIMESTAMP WITH TIME ZONE: Timestamps with timezone awareness for temporal data

##### JSONB: Binary data with JSON validation and efficient storage

##### BYTEA: Binary data for small files, images, or serialized objects

### Constraints enforce data integrity rules

- PRIMARY KEY ensures each row has a unique identifier
- NOT NULL prevents missing values in critical columns
- UNIQUE prevents duplicate values in columns that should be unique
- CHECK enforces business rules or data validation
- FOREIGN KEY establishes relationships between tables

### The following example creates a table for storing AI conversation sessions:

#### SQL
```sql
CREATE TABLE conversations (
    id BIGSERIAL PRIMARY KEY,
    session_id UUID NOT NULL,
    user_id VARCHAR(255) NOT NULL,
    started_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    ended_at TIMESTAMP WITH TIME ZONE,
    status VARCHAR(50) CHECK (status IN ('pending', 'active', 'completed')),
    metadata JSONB DEFAULT '{}'::jsonb
);
```

### This example demonstrates several important schema design principles:

##### Auto-incrementing primary key using BIGSERIAL

##### UUID for unique session identifiers

##### NOT NULL constraints on critical fields (user_id, started_at, ended_at)

##### CHECK constraint for status validation

##### JSONB column for flexible metadata storage

## Manage schemas

- Schemas group related database objects and provide logical separation
- You can create, modify, and drop schemas using standard SQL DDL statements

### Create a schema

#### SQL
```sql
CREATE SCHEMA ai_application;
```

### Create tables within a schema

#### SQL
```sql
CREATE TABLE ai_application.conversations (
    id BIGSERIAL PRIMARY KEY,
    -- Other column definitions
);
```

### The schema name prefix provides organization and clarity

- Use schema prefixes to group related objects and prevent naming conflicts

### Drop a schema

#### SQL
```sql
DROP SCHEMA ai_application CASCADE;
```

- The CASCADE option drops all dependent objects automatically

### Alter a schema

#### Add a new column

#### SQL
```sql
ALTER TABLE ai_application.conversations
ADD COLUMN category VARCHAR(100);
```

#### Drop a column

#### SQL
```sql
ALTER TABLE ai_application.conversations
DROP COLUMN category;
```

- Be careful with DROP COLUMN as it may cause data loss if the column contains data

## Use appropriate data types

- Choosing the right data types affects storage efficiency, query performance, and application functionality

### For AI applications, consider these data type recommendations:

#### Use UUID for identifiers

- Provides universally unique identifiers without collision risk
- More efficient than BIGSERIAL for distributed systems
- Supported by all PostgreSQL tools and frameworks

#### Use TEXT for variable-length text content

- No length limit like VARCHAR(n)
- More efficient than TEXT for shorter strings
- Supports full-text search and indexing capabilities

#### Use TIMESTAMP WITH TIME ZONE for temporal data

- Stores timezone-aware timestamps
- Essential for applications that operate across multiple time zones
- Default to current timestamp when no value is specified

#### Use JSONB for semi-structured data

- Stores JSON data in binary format with validation
- Efficient for storing configuration, metadata, or flexible data structures
- Supports indexing and querying of JSON fields

#### Use BYTEA for binary data

- Stores small files, images, or serialized objects efficiently
- More space-efficient than TEXT for binary data
- Useful for storing model files, images, or embeddings

## Implement constraints effectively

- Constraints are your first line of defense for data integrity

### Primary key constraints

- Every table should have a primary key for unique row identification
- Composite primary keys for many-to-many relationships
- Consider using UUID or BIGSERIAL based on your requirements

### Foreign key relationships

- Enforce referential integrity between related tables
- Choose appropriate actions for updates and deletes (RESTRICT vs. CASCADE)
- Consider ON DELETE SET NULL for soft deletes that preserve data integrity

### Check constraints

- Validate data at the database level rather than just in application
- Use CHECK constraints for business rule enforcement
- Ensure constraint names are descriptive and meaningful

## Schema evolution strategies

### Version your schemas

- Include version numbers in schema names for backward compatibility
- Use migration scripts to handle schema changes across environments
- Test schema changes thoroughly before deploying to production

### Use migration tools

- PostgreSQL provides tools like pg_dump and pg_restore for logical backups
- Azure Database Migration service for large-scale schema changes
- Consider blue-green deployments for zero-downtime schema updates
