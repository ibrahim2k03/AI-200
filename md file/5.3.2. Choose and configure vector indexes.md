# 5.3.2. Choose and configure vector indexes

Completed
100 XP
15 minutes

Vector indexes enable fast similarity search by organizing vectors into data structures that eliminate the need to compare every stored vector against each query. Choosing the right index type and configuring its parameters correctly determines whether your AI application meets its performance targets.

 Note

Code examples in this unit show index creation patterns for pgvector. Index parameter recommendations are starting points based on general guidance. Optimal values depend on your dataset characteristics, accuracy requirements, and performance constraints. Always benchmark with representative data before deploying to production.

Understanding vector index types
Azure Database for PostgreSQL supports three vector index types, each optimized for different dataset sizes and accuracy requirements. Understanding the trade-offs helps you select the right approach for your AI application.

IVFFlat indexes
IVFFlat (Inverted File Flat) indexes partition vectors into clusters, then search only relevant clusters at query time. This approach reduces the search space while maintaining reasonable accuracy.

Key characteristics:
- Partitions vectors into lists (clusters) based on k-means clustering
- Searches only within most relevant clusters (controlled by probes parameter)
- Provides 95-99% recall with appropriate configuration
- Build time: O(N × k) where N is number of vectors, k is number of lists
- Memory usage: Lower than HNSW, approximately 1.5x vector data size
- Index size: Smaller than HNSW, approximately 1.1x vector data size
- Best for: Medium datasets (1,000-50,000 vectors) with good accuracy requirements

Use IVFFlat when:
- Dataset size is moderate (up to 50,000 vectors per partition)
- You need 95-99% recall with sub-millisecond query latency
- Memory constraints exist (limited available RAM)
- Build time is acceptable (minutes, not hours)
- Data distribution is relatively stable (doesn't change frequently)

HNSW indexes
HNSW (Hierarchical Navigable Small World) indexes organize vectors into a multi-layer graph structure for efficient navigation. This approach typically provides the best performance for large datasets.

Key characteristics:
- Organizes vectors into a graph with multiple layers
- Uses coarse-to-fine search: starts broad, narrows down progressively
- Provides 99%+ recall with appropriate configuration
- Build time: O(N log N) where N is number of vectors
- Memory usage: Higher than IVFFlat, approximately 2x vector data size
- Index size: Larger than IVFFlat, approximately 2x vector data size
- Best for: Large datasets (50,000+ vectors per partition)

Use HNSW when:
- Dataset size is large (50,000+ vectors per partition)
- You need 99%+ recall with millisecond query latency
- Memory is available (sufficient RAM for graph structure)
- Build time is acceptable (can be hours for very large datasets)
- Data distribution may change frequently (requires periodic index rebuilds)

DiskANN indexes
DiskANN (Disk Approximate Nearest Neighbor) indexes are Azure-specific and provide excellent performance for very large datasets.

Key characteristics:
- Uses Microsoft Research's DiskANN algorithm optimized for SSD storage
- Provides 99%+ recall with millisecond query latency
- Build time: O(N log N) but optimized for large datasets
- Memory usage: Highest of all index types
- Index size: Largest of all index types
- Best for: Enterprise-scale datasets (millions of vectors)

Use DiskANN when:
- Dataset size is very large (millions of vectors)
- You need maximum performance with acceptable recall
- Memory is abundant (sufficient RAM for large graph structures)
- Build time is acceptable (hours to days for very large datasets)
- Cost is justified by performance gains at scale

Choosing between index types
Decision matrix for index selection:

| Dataset Size | Recall Requirement | Latency Requirement | Recommended Index |
|---|---|---|---|---|
| < 10K | Any | Any | Sequential scan (no index) |
| 10K-50K | 95% | < 100ms | IVFFlat |
| 50K-500K | 95% | < 50ms | IVFFlat or HNSW |
| 500K-1M | 95% | < 20ms | HNSW |
| 1M-10M | 95% | < 10ms | HNSW |
| 10M+ | 95% | < 10ms | DiskANN |

For most production AI applications with large vector datasets, DiskANN provides the best combination of high recall and low latency.

Index configuration parameters
Each index type accepts configuration parameters that affect performance and accuracy. Understanding these parameters helps you tune indexes for your specific workload.

IVFFlat parameters:
- lists: Number of clusters to create (default: 100)
- probes: Number of clusters to search per query (default: 1)
- Higher lists = better recall but slower queries
- Higher probes = better recall but slower queries
- Optimal probes = sqrt(lists) for balanced performance

HNSW parameters:
- m: Connections per node in the graph (default: 16)
- ef_construction: Search width during index building (default: 64)
- ef_search: Search width during queries (default: 40)
- Higher m = better recall but more memory usage
- Higher ef_construction = better index quality but longer build times
- Higher ef_search = better recall but slower queries

DiskANN parameters:
- DiskANN-specific parameters for tuning performance
- IndexingSearchListSize: Controls build-time vs. query-time trade-off
- quantizationByteSize: Controls storage vs. accuracy trade-off
- Additional DiskANN parameters available through Azure portal

Creating indexes
Use appropriate CREATE INDEX syntax for your chosen index type. Always specify the operator class that matches your distance function.

IVFFlat index creation:
SQL
-- Create IVFFlat index with optimized parameters
CREATE INDEX ON products
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 1000, probes = 10);

-- Verify index creation
EXPLAIN ANALYZE 
SELECT * FROM products 
WHERE embedding <=> '[0.0123, -0.0456, ...]'::vector 
LIMIT 5;
The output should show "Index Scan using products_embedding_idx" if the index is being used correctly.

HNSW index creation:
SQL
-- Create HNSW index with optimized parameters
CREATE INDEX ON products
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- Verify HNSW index usage
EXPLAIN ANALYZE 
SELECT * FROM products 
WHERE embedding <=> '[0.0123, -0.0456, ...]'::vector 
LIMIT 5;
The output should show "Index Scan using products_embedding_idx" with the HNSW index being used effectively.

DiskANN index creation:
SQL
-- Create DiskANN index (Azure-specific)
CREATE INDEX ON products
USING diskann (embedding vector_cosine_ops);
DiskANN indexes are automatically configured by Azure Database for PostgreSQL and may not require additional parameters for basic usage.

Index maintenance strategies
As your data evolves, indexes need maintenance to maintain performance:

Monitor index statistics:
SQL
-- Check index size and usage
SELECT 
    schemaname,
    relname,
    indexname,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
    pg_size_pretty(pg_indexes_size(relid)) AS indexes_size
FROM pg_stat_user_indexes 
WHERE schemaname = 'ai_application' 
    AND relname = 'products';

-- Monitor query performance
EXPLAIN ANALYZE 
SELECT * FROM products 
WHERE embedding <=> '[0.0123, -0.0456, ...]'::vector 
LIMIT 10;

Rebuild indexes when needed:
SQL
-- Rebuild HNSW index concurrently
REINDEX INDEX CONCURRENTLY products_embedding_idx;

-- Rebuild IVFFlat index with new parameters
DROP INDEX IF EXISTS products_embedding_idx;
CREATE INDEX ON products
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 2000, probes = 15);

-- Verify new index
EXPLAIN ANALYZE 
SELECT * FROM products 
WHERE embedding <=> '[0.0123, -0.0456, ...]'::vector 
LIMIT 5;
Performance monitoring
Track key metrics to ensure indexes are working effectively:

Index hit ratio: Percentage of queries using indexes vs. sequential scans
Query latency: Average response time for vector queries
Index size: Storage used by indexes
Recall: Percentage of relevant documents returned

Set up alerts for:
- High query latency (> 100ms)
- Low index hit ratio (< 80%)
- Sequential scans on large tables

Best practices
Choose index type based on dataset size and requirements
Start with conservative parameters and tune based on benchmarks
Monitor performance continuously and adjust parameters as needed
Use CONCURRENTLY for index rebuilds in production
Test index changes in staging before deploying to production
