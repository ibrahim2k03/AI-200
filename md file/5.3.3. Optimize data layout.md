# 5.3.3. Optimize data layout

Completed
100 XP
14 minutes

Data modeling decisions significantly affect vector search performance. How you structure tables, choose data types for metadata, and create supporting indexes determines whether queries execute efficiently as your dataset grows. Understanding these patterns helps you make informed decisions about schema design and query optimization.

 Note

Code examples in this unit demonstrate schema design patterns for vector data with metadata. Adapt these patterns to your specific data model and query requirements.

Vector storage considerations
Vector columns consume substantial storage and processing resources. Understanding storage characteristics helps you make informed decisions about schema design and resource allocation.

Storage impact analysis:
Each vector dimension adds 4 bytes of storage (for single-precision float). The relationship between dimensions and storage is linear:

Dimensions	Storage per vector	1 million vectors
384	~1.5 GB	~1.5 GB
768	~3 GB	~3 GB
1536	~6 GB	~6 GB
3072	~12 GB	~12 GB
For a product catalog with two million items using 1536-dimensional embeddings, the vector column alone requires approximately 12 GB of storage. Adding metadata columns increases this proportionally. When you reach tens of millions of items, vector storage becomes a major cost factor.

Storage optimization strategies:
Choose appropriate vector dimensions based on your accuracy requirements. Lower-dimensional embeddings reduce storage costs but may sacrifice semantic precision. Higher-dimensional embeddings capture more nuance but increase storage and computation costs.

Consider using halfvec (16-bit) instead of vector (32-bit) to reduce storage by 50% with minimal accuracy loss for many use cases. This reduces storage from 6 GB to 3 GB for the same dataset size.

SQL
CREATE TABLE products (
    id BIGSERIAL PRIMARY KEY,
    name TEXT NOT NULL,
    embedding halfvec(1536)  -- 50% storage reduction
    category_id INTEGER
    price NUMERIC(10,2)
);
For recommendation engines where dot product similarity is sufficient, halfvec maintains relative ordering while cutting storage costs. For cosine similarity applications, ensure your vectors are normalized before storing as halfvec to maintain semantic relationships.

Metadata storage strategies:
Store frequently accessed metadata in separate columns rather than JSONB for better query performance. Structured columns enable B-tree indexes for efficient filtering and sorting.

SQL
CREATE TABLE products (
    id BIGSERIAL PRIMARY KEY,
    name TEXT NOT NULL,
    embedding vector(1536),
    category_id INTEGER NOT NULL,  -- Indexed for filtering
    price NUMERIC(10,2) NOT NULL,        -- Indexed for range queries
    in_stock BOOLEAN DEFAULT true,           -- Indexed for boolean filtering
    brand TEXT,                            -- Non-indexed, accessed rarely
    rating NUMERIC(2,1)               -- Non-indexed, used for sorting
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP  -- Indexed for temporal queries
);
This design enables efficient queries on category, price range, stock status, and creation date while keeping less frequently accessed data in flexible JSONB format.

Data type selection:
Choose appropriate PostgreSQL data types for your use case to optimize storage and query performance.

For vector data:
- vector/float4: Standard single-precision, good balance of precision and storage
- vector/halfvec: 16-bit precision, 50% storage reduction with minimal accuracy loss
- vector/int8: 8-bit integer, maximum compression (75% storage reduction) for specific use cases

For metadata:
- Use native types (INTEGER, TIMESTAMP, NUMERIC, TEXT) for structured data
- Use JSONB only for truly flexible or hierarchical data
- Use arrays for simple lists (tags, categories) when order doesn't matter

Indexing strategy:
Create indexes on columns that are frequently used in WHERE clauses, ORDER BY, and JOIN conditions. Avoid indexing rarely accessed columns or large text fields that are never filtered.

SQL
-- Indexes for common query patterns
CREATE INDEX idx_products_category ON products (category_id);
CREATE INDEX idx_products_price ON products (price);
CREATE INDEX idx_products_instock ON products (in_stock);
CREATE INDEX idx_products_created ON products (created_at);

-- Composite index for category + price filtering
CREATE INDEX idx_products_category_price ON products (category_id, price);
This composite index efficiently handles queries that filter by category and sort by price range, a common e-commerce pattern.

Query optimization patterns:
Design queries to use indexes effectively and minimize the amount of data processed.

Filter before vector search:
Apply WHERE clauses to reduce the number of vectors that need similarity calculations. This is the most effective optimization for vector queries.

SQL
-- Efficient filtering before vector search
SELECT id, name, embedding <=> $1 AS distance
FROM products
WHERE category_id = 5
  AND price BETWEEN 100 AND 500
ORDER BY embedding <=> $1
LIMIT 10;
This query first uses the category index to find matching products, then applies the price range filter, then performs vector similarity only on the reduced set. The vector distance calculation happens on approximately 1% of the original dataset instead of 100%.

Use appropriate LIMIT clauses:
Limit the number of results to reduce computation and data transfer. For RAG applications, consider both the number of documents returned and the total token count to stay within LLM context limits.

SQL
-- Limit results for RAG context
SELECT id, name, embedding <=> $1 AS distance
FROM products
WHERE category_id = 5
ORDER BY embedding <=> $1
LIMIT 5;  -- Return only top 5 most similar
For applications that need more context, increase the LIMIT but implement context window retrieval to get surrounding documents.

Projection optimization:
Select only the columns needed for your application rather than using SELECT *. This reduces data transfer and improves query performance.

SQL
-- Project only needed columns
SELECT id, name, price, embedding <=> $1 AS distance
FROM products
WHERE category_id = 5
ORDER BY embedding <=> $1
LIMIT 5;
This query returns only the essential columns (id, name, price, distance) instead of all columns, reducing I/O and memory usage.

Batch processing:
For bulk operations, use PostgreSQL's COPY command instead of individual INSERT statements. This can be 10-100x faster for large data loads.

SQL
-- Efficient bulk load using COPY
COPY products (id, name, category_id, price, in_stock, brand, rating, created_at)
FROM '/path/to/products.csv'
WITH (FORMAT csv, HEADER);
The COPY command is PostgreSQL's fastest method for bulk data loading, especially when loading millions of rows.

Connection management:
Use connection pooling to reduce the overhead of establishing new connections for each query.

SQL
-- Connection pool configuration
CREATE EXTENSION IF NOT EXISTS pgbouncer;
-- Configure PgBouncer for optimal performance
ALTER SYSTEM SET pgbouncer.pool_mode = 'transaction';
ALTER SYSTEM SET pgbouncer.max_client_conn = 100;
ALTER SYSTEM SET pgbouncer.default_pool_size = 20;
For high-concurrency applications, use transaction mode to maintain consistency across related operations within a single database connection.

Performance monitoring:
Regularly analyze query performance and index usage to identify optimization opportunities.

SQL
-- Monitor index effectiveness
EXPLAIN ANALYZE SELECT id, name, embedding <=> $1 AS distance
FROM products
WHERE category_id = 5
ORDER BY embedding <=> $1
LIMIT 5;
The output shows whether the index is being used and the estimated cost. Look for "Index Scan" vs "Index Scan" to verify index usage.

-- Check index statistics
SELECT 
    schemaname,
    relname,
    indexname,
    idx_scan,
    idx_tup_fetch,
    idx_tup_read,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
    pg_size_pretty(pg_indexes_size(relid)) AS indexes_size
FROM pg_stat_user_indexes 
WHERE schemaname = 'public' 
    AND relname = 'products';
Monitor index hit ratios and query latency to ensure your optimizations are effective. Low hit ratios or increasing latency indicate that indexes may need adjustment or query patterns should be reviewed.
