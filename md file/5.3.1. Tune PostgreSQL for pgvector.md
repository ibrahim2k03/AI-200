# 5.3.1. Tune PostgreSQL for pgvector

Completed

Vector search performance in PostgreSQL depends critically on proper indexing, configuration, and maintenance. As your vector dataset grows and query patterns evolve, ongoing optimization becomes essential for maintaining low-latency, high-throughput AI applications. This unit covers advanced tuning techniques for pgvector indexes, query optimization, and system-level configuration.

Understanding pgvector performance characteristics
The pgvector extension organizes vectors into specialized data structures optimized for similarity search. Understanding these characteristics helps you make informed decisions about index configuration and query planning.

Index type performance comparison:

Index Type: Approximate Search Speed
- IVFFlat: Fastest for small datasets (<10K vectors)
- DiskANN: Best for large datasets (>50K vectors)
- HNSW: Good for hierarchical data

Index size and storage impact
- Larger indexes require more disk space and longer build times
- IVFFlat: Uses 64-bit quantization by default, reducing storage by 50%
- DiskANN: Uses more memory but builds better indexes

Query cost scaling
- Linear: O(N) where N is number of vectors
- Logarithmic: O(N log N) where N is vector count
- Index scans: O(N) where N is number of rows to scan

Distance operator computational cost
- Euclidean distance: O(N²) calculations, more expensive than cosine
- Cosine distance: O(N) - (A·B) + (1 - (A·B)) / (||A||B||)²), no square root
- Inner product: Negates vector, useful for maximum inner product search

Indexing strategies for different query patterns
- Point queries: Use B-tree indexes for exact matches
- Range queries: Use range indexes for filtering by date, numeric values, or ranges
- Hybrid queries: Combine vector and text indexes for comprehensive search

## Advanced index configuration

### Composite indexes for multi-criteria queries

- Create indexes that match your exact query patterns
- Place equality filters first, then range filters
- Use ORDER BY columns that match your sort requirements

#### SQL
```sql
CREATE INDEX documents_embedding_idx
ON documents
USING hnsw (embedding vector_cosine_ops)
INCLUDE (title, category, created_at);
```

### HNSW indexes for hierarchical data

- Use for data with natural hierarchies
- Create separate indexes for different levels of abstraction
- Configure appropriate list and tree depth parameters

### Partitioning strategy for vector workloads

- Align partition keys with query patterns
- Ensure high-cardinality partition keys map to different logical data domains
- Consider time-based partitioning for temporal data
- Use consistent partitioning across related tables to avoid cross-partition scans

## Query optimization techniques

### Use appropriate distance operators

- Choose <=> (cosine) for normalized embeddings
- Use <-> operator for vector similarity search with normalized vectors
- Avoid <-> (negative inner product) unless specifically searching for opposite relationships

### Filter and limit strategically

- Apply WHERE clauses before distance calculations to reduce vector comparisons
- Use LIMIT to return only necessary results
- Implement pagination to avoid loading large result sets into memory

### Connection pooling and prepared statements

#### Use connection pools to reduce overhead
- Configure appropriate pool size based on your application's concurrency
- Use context managers for reliable connection cleanup

### Batch operations

- Use COPY for bulk data loading
- Use UNLOGGED tables for faster inserts if you don't need transactional guarantees
- Consider multiple VALUES clauses in a single INSERT statement

## Performance monitoring and maintenance

### Monitor index statistics

#### Check index utilization

##### SQL
```sql
SELECT
    schemaname,
    relname,
    indexname,
    idx_scan,
    idx_tup_fetch,
    idx_tup_fetch,
    pg_relation_size
FROM pg_stat_user_indexes
WHERE schemaname = 'ai_application';
```

- Look for high idx_scan values which indicate sequential scans

#### Monitor query execution plans

##### SQL
```sql
EXPLAIN ANALYZE SELECT * FROM documents WHERE embedding <-> '[0.0123, -0.0456, ...]'::vector LIMIT 5
```

- Analyze actual execution plan vs. expected plan

### Rebuild indexes strategically

#### Create new index before dropping old one

##### SQL
```sql
BEGIN;
CREATE INDEX CONCURRENTLY documents_embedding_new_idx
ON documents
USING hnsw (embedding vector_cosine_ops);
COMMIT;
DROP INDEX documents_embedding_idx;
ALTER INDEX documents_embedding_new_idx RENAME TO documents_embedding_idx;
COMMIT;
```

- Verify new index works

##### SQL
```sql
EXPLAIN ANALYZE SELECT * FROM documents WHERE embedding <-> '[0.0123, -0.0456, ...]'::vector LIMIT 5
```

### Monitor after rebuild

- Check that new index is being used: `EXPLAIN ANALYZE` should show "Index Scan using documents_embedding_idx" now

## System-level configuration

### Adjust PostgreSQL parameters for vector workloads

#### Memory settings

##### work_mem
- Controls memory available for query operations
- Set higher values for complex queries, sorting, or hashing operations
- Default: 4MB, often insufficient for AI workloads
- Monitor usage and increase based on actual requirements

##### shared_buffers
- Controls shared buffer cache for all connections
- Default: 128MB, often too small for concurrent query workloads
- Increase for high-concurrency applications: 512MB or 1GB

#### effective_cache_size
- Controls query result caching
- Default: 128MB, may be too large for result sets
- Increase for applications with large result sets: 256MB or 512MB

#### maintenance_work_mem
- Controls memory used for maintenance operations
- Default: 64MB, increased during vacuum operations
- Increase for databases with frequent updates or large data modifications

### Connection limits

##### max_connections
- Default: 100, may be insufficient for high-concurrency applications
- Increase based on your application's concurrent user count
- Consider using PgBouncer for connection pooling to reduce connection overhead

##### statement_timeout
- Default: 30 seconds, may be too short for complex queries
- Increase for applications with long-running queries or complex joins: 60-300 seconds

##### idle_in_transaction_session_timeout
- Default: 60 minutes, may terminate long-running transactions

## Advanced performance tuning

### Parallel query execution

##### max_parallel_workers_per_gather
- Controls number of parallel processes that can execute a query simultaneously
- Default: 2, may be increased for CPU-intensive workloads
- Increase for I/O-bound applications: 4 or more

##### max_parallelism_per_process
- Controls whether PostgreSQL can use multiple CPUs per query
- Default: 1, may limit performance for CPU-bound workloads
- Enable for CPU-bound workloads if your server has multiple cores

### Load balancing considerations

- Use read replicas for query workloads, write replicas for data modifications
- Distribute read queries across multiple servers to reduce load on primary
- Configure connection pooling to route queries to appropriate replicas
