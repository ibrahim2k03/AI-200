## Establishing secure connections to Azure Database for PostgreSQL requires understanding connection string components, authentication options, and transport layer security configuration

- For AI applications that frequently read and write data, getting connection configuration right from the start prevents authentication failures and security vulnerabilities in production
- Azure Database for PostgreSQL uses a specific endpoint format and enforces secure transport by default
- Different client libraries and tools accept these parameters in various formats, including connection strings, keyword-value pairs, or individual parameters

## Connection fundamentals

- PostgreSQL connections require several parameters that identify the server, database, and user credentials
- Azure Database for PostgreSQL uses a specific endpoint format and enforces secure transport by default

### Your server endpoint follows the pattern <server-name>.postgres.database.azure.com

- Where <server-name> is the unique name you specified when creating the server
- The fully qualified domain name (FQDN) resolves to the server's public IP address when using public access, or a private IP address when using VNet integration

### A PostgreSQL connection requires these core parameters:

#### host (server FQDN): The server name or IP address

#### port (5432 for direct connections or 6432 for PgBouncer)

#### database name: The specific PostgreSQL database to connect to

#### username: The database user account name

#### password: The password for PostgreSQL native authentication

#### sslmode: Controls TLS/SSL encryption settings

### Different client libraries and tools accept these parameters in various formats

- Connection strings combine all parameters in a single string
- Keyword-value pairs work well for configuration files
- Individual parameters provide flexibility for programmatic connections
- Most PostgreSQL clients support multiple authentication methods

## Authentication methods

- Azure Database for PostgreSQL supports two primary authentication approaches: Microsoft Entra authentication and PostgreSQL native authentication

### Microsoft Entra authentication provides stronger security through token-based access

- Uses OAuth 2.0 tokens instead of passwords
- This approach integrates with Azure's identity platform and provides centralized identity management
- Supports managed identities for Azure-hosted applications, eliminating the need to store secrets in application configuration
- Creates audit trails in Entra sign-in logs for security compliance

- To use Entra authentication, configure a Microsoft Entra administrator on your server (a user account, group, or service principal)

- Once configured, Entra identities connect by obtaining a token from https://ossrdbms-aad.database.windows.net

### PostgreSQL native authentication stores usernames and encrypted passwords

- Traditional approach using database users with specific permissions
- Appropriate when applications can't use Entra authentication (legacy applications, cross-tenant access)
- Requires careful password management, rotation policies, and access control through database roles

### The connection process works as follows:

#### Your application requests an access token from Microsoft Entra ID

#### Entra validates the identity and returns a token

#### Your application connects to PostgreSQL using the token as the password

#### PostgreSQL validates the token against the configured Entra administrator

### In Python, you can use the azure-identity library to obtain tokens automatically

#### Python
```python
from azure.identity import DefaultAzureCredential

credential = DefaultAzureCredential()
token = credential.get_token("https://ossrdbms-aad.database.windows.net/.default")

# Use token.token as the password in your connection string
connection_string = f"postgresql://user@myserver.postgres.database.azure.com:6432/mydb?sslmode=require"
```

### The DefaultAzureCredential class automatically tries multiple authentication methods in order

- Managed identity (when running on Azure)
- Azure CLI credentials (for local development)
- Environment variables (for deployed applications)

### PostgreSQL native authentication stores usernames and encrypted passwords in the database

- Use this approach when applications can't use Entra authentication
- Implement strong password policies: minimum length, complexity requirements, regular rotation
- Store passwords in Azure Key Vault rather than application configuration
- Use database roles to limit user permissions to least privilege required

## TLS/SSL configuration

- Azure Database for PostgreSQL encrypts all connections using Transport Layer Security (TLS) by default

- The server requires TLS by default and supports TLS 1.2 and 1.3
- Connections using older TLS versions are rejected

### PostgreSQL clients use the sslmode parameter to control encryption and certificate validation

#### The available modes are:

##### disable: No encryption

##### allow: Encrypts if the server requires it, but doesn't validate certificates

##### prefer: Encrypts if the server supports it, but doesn't validate certificates

##### require: Enforces encryption and validates server certificate against trusted certificate authorities

##### verify-ca: Enforces encryption, validates CA, and confirms certificate hostname matches server

##### verify-full: Enforces encryption, validates CA, and confirms certificate's common name or subject alternative name matches server

### For production applications, use verify-full to ensure you're connecting to a genuine Azure PostgreSQL server

- This mode validates that the server presents a certificate signed by a trusted certificate authority and that the certificate's common name or subject alternative name matches the server hostname

- Most operating systems and Azure hosting environments already include the DigiCert and Microsoft root CAs that Azure Database for PostgreSQL uses

### Connection string examples for different SSL modes

#### Basic connection with SSL required

##### Connection string
```postgresql://myuser:mypassword@myserver.postgres.database.azure.com/mydb?sslmode=require
```

#### Connection with certificate verification

##### Connection string
```postgresql://myuser:mypassword@myserver.postgres.database.azure.com/mydb?sslmode=verify-full&sslrootcert=/etc/ssl/certs/ca-certificates.crt
```

#### Connection through PgBouncer (note port 6432)

##### Connection string
```postgresql://myuser:mypassword@myserver.postgres.database.azure.com:6432/mydb?sslmode=require
```

## Connection pooling with PgBouncer

- Azure Database for PostgreSQL includes built-in PgBouncer, which you can enable through server configuration or using the Azure CLI

- PgBouncer maintains a pool of connections to the database server and multiplexes client connections onto this pool
- This reduces the overhead of connection establishment, which is valuable for applications that make many short-lived database calls

### Important

#### PgBouncer is only available on General Purpose and Memory Optimized compute tiers

- If your server uses the Burstable tier, you can't enable built-in PgBouncer

#### Once enabled, connect on port 6432 instead of the standard PostgreSQL port 5432

### Connection pooling optimization strategies

#### Pool sizing: Configure max_client_conn to match your application's concurrent connection needs

#### Transaction vs. session modes: Choose session mode for applications with long-running transactions, pool mode for applications with many short queries

#### Timeout settings: Configure server_reset_query and server_check_delay to optimize connection reuse

### Enable PgBouncer using Azure CLI

#### Azure CLI
```bash
az postgres flexible-server parameter set \
    --resource-group myResourceGroup \
    --server-name myserver \
    --name pgbouncer.enabled \
    --value true
```

#### After enabling, update your connection string to use port 6432

##### Connection string
```postgresql://myuser:mypassword@myserver.postgres.database.azure.com:6432/mydb?sslmode=require
```

## Network access considerations

- Azure Database for PostgreSQL supports two networking models that control how clients can connect to your database

### Public access with firewall rules

- The server has a public IP address and firewall rules control which client IPs can connect
- You can configure firewall rules to allow access from specific IP addresses or ranges
- This approach provides network isolation but requires careful IP management

### Private access with VNet integration

- The server has only a private IP address within an Azure Virtual Network
- You can only connect from resources within the same VNet, peered networks, or through VPN/ExpressRoute
- This provides enhanced security and network isolation for production environments

### Connection string examples for different network configurations

#### Public access

##### Connection string
```postgresql://myuser:mypassword@myserver.postgres.database.azure.com/mydb
```

#### Private access with VNet

##### Connection string
```postgresql://myuser:mypassword@myserver.postgres.database.azure.com/mydb
```

## Best practices

### Use Microsoft Entra authentication for production applications

- Provides stronger security through token-based access and centralized identity management
- Eliminates password storage and rotation requirements
- Integrates with Azure's security infrastructure and audit capabilities

### Use connection pooling for AI applications

- AI applications often make many short-lived database connections
- PgBouncer or similar pooling mechanisms reduce connection overhead
- Configure appropriate pool sizes based on your application's concurrency requirements

### Implement secure connection management

- Use SSL/TLS for all connections in production
- Store connection strings in Azure Key Vault rather than application configuration
- Implement connection retry logic with exponential backoff
- Monitor connection performance and adjust pool sizes as needed

### Choose appropriate compute and storage tiers

- Monitor resource utilization and adjust based on actual requirements
- Consider auto-scaling for workloads with variable traffic patterns
- Use reserved capacity for predictable workloads with consistent resource requirements
