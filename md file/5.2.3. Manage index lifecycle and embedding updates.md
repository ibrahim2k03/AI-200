# 5.2.3. Manage index lifecycle and embedding updates

Completed
100 XP
10 minutes

Vector indexes and embeddings require ongoing maintenance as your data evolves. New documents shift the distribution of vectors, content changes invalidate existing embeddings, and embedding model upgrades require regenerating all vectors. Understanding how to manage these changes efficiently keeps your vector search performing well over time.

This unit assumes familiarity with PostgreSQL's vector extension and indexing concepts. If you need a refresher on basic vector operations, see Get started querying with Transact-SQL learning path is a good resource.

Index health monitoring
Effective index maintenance starts with understanding current index state and performance. PostgreSQL provides several system views and functions that reveal how efficiently queries use indexes.

Key metrics to track:

Index utilization: Percentage of queries that use indexes versus those that perform scans
Query cost: Total RUs consumed by queries using indexes
Index size: Storage consumed by indexes on disk
Index hit ratio: How often queries successfully use indexes
Query latency: Average time for different query types

PostgreSQL system views for index statistics:

SQL
SELECT
    schemaname,
    relname,
    indexname,
    idx_scan,
    idx_tup_fetch,
    idx_tup_fetch,
    pg_relation_size
FROM pg_stat_user_indexes
WHERE schemaname = 'ai_application';
The pg_stat_user_indexes view shows which indexes exist, their types, and usage statistics. Monitor this view regularly to identify indexes that aren't being used or that show high scan rates.

Index size and performance analysis
The pg_indexes_size view shows storage consumption of indexes in bytes. Compare this to your actual data size to identify over-indexed tables.

SQL
SELECT
    schemaname,
    SUM(pg_total_relation_size('ai_application')) AS total_db_size,
    SUM(pg_indexes_size('ai_application')) AS total_index_size,
    ROUND((total_index_size::numeric / total_db_size) * 100, 2) AS index_percentage
FROM pg_indexes_size;
This query calculates percentage of database storage used by indexes. If your index_percentage is significantly higher than expected, you may have over-indexed tables that aren't actively queried.

Query performance analysis
Use EXPLAIN ANALYZE to understand query execution plans:

SQL
EXPLAIN ANALYZE SELECT * FROM documents WHERE embedding <-> '[0.0123, -0.0456, ...]'::vector LIMIT 10;
The output shows whether PostgreSQL uses your vector index or performs a sequential scan. Look for "Index Scan using documents_embedding_idx" versus "Bitmap Heap Scan." A sequential scan indicates that your vector index isn't being used effectively.

Index maintenance strategies
Regular vacuuming maintains index performance by removing dead tuples and updating statistics. Configure appropriate autovacuum settings for your workload:

SQL
ALTER TABLE documents SET (
    autovacuum_vacuum_scale_factor = 0.05,
    autovacuum_analyze_scale_factor = 0.02
);
For tables with frequent updates, consider increasing the scale factor to reduce vacuum frequency. For tables with heavy inserts, use scale factor 0.1 to run vacuum more often.

Rebuilding indexes for data changes
When you need to change index structure (such as adding new columns or changing distance functions), create a new index and drop the old one:

SQL
-- Create new index with updated structure
CREATE INDEX documents_embedding_new_idx
ON documents
USING hnsw (embedding vector_cosine_ops);

-- Swap index atomically
DROP INDEX documents_embedding_idx;
ALTER INDEX documents_embedding_new_idx RENAME TO documents_embedding_idx;
CREATE INDEX documents_embedding_idx
ON documents
USING hnsw (embedding vector_cosine_ops);

-- Verify new index works
EXPLAIN ANALYZE SELECT * FROM documents WHERE embedding <-> '[0.0123, -0.0456, ...]'::vector LIMIT 10;
If the output shows "Index Scan using documents_embedding_idx," the rebuild failed and old index is still active.

Embedding update strategies
When content changes in documents require new embeddings, update them efficiently using batch operations:

SQL
-- Batch update using VALUES clause
UPDATE documents
SET embedding = '[0.0234, -0.0567, ...]'::vector
WHERE id IN (1, 2, 3);

-- Use parameterized updates for consistency
UPDATE documents
SET embedding = $1
WHERE id = $1;

-- Update only changed rows
UPDATE documents
SET embedding = $1
WHERE id = $1 AND content LIKE '%updated%'
    AND updated_at > CURRENT_TIMESTAMP - INTERVAL '1 day';
This approach updates only rows that actually changed, reducing unnecessary embedding API calls.

-- Update with conditionals for partial updates
UPDATE documents
SET content = CASE
    WHEN content LIKE '%urgent%' THEN '[0.0345, -0.0678, ...]'::vector
    WHEN content LIKE '%standard%' THEN '[0.0456, -0.0789, ...]'::vector
    ELSE embedding
END
WHERE id = $1;
This conditional update applies different embeddings based on content categories, using a single statement to update multiple rows efficiently.

## Performance monitoring

### Track embedding generation costs

- Embedding API calls typically have rate limits and costs
- Monitor usage through your embedding provider's dashboard
- Implement batch processing to reduce API calls
- Consider caching embeddings for frequently used content to avoid regeneration

### Index usage patterns

- Monitor which indexes are actively used in queries
- Identify indexes that show high scan rates or low hit ratios
- Consider removing unused indexes to reduce storage costs and maintenance overhead

### Automated maintenance

- Schedule regular vacuuming during low-traffic periods
- Set up monitoring alerts for high index utilization or query latency
- Consider automated index rebuilds when data distribution changes significantly
