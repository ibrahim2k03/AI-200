# Registries, repositories, and artifacts

## Azure Container Registry
- Managed private Docker registry for storing and distributing container images and artifacts.
  - ACR provides:
    - Direct access control - manage who can push and pull images
    - Geo-replication for global distribution
    - Integration with AKS and Container Apps - seamless deployments

### ACR capabilities for AI workloads:
- **Private storage**: Secure model serving images, preprocessing containers, and inference APIs in Azure
- **Geo-replication**: Distribute images near deployment regions for faster pulls and lower latency
- **Integration**: Direct connection to AKS, Container Apps, and App Service for seamless deployments
- **Content formats**: Store Docker images, Helm charts, and OCI artifacts in one registry

### ACR service tiers:
- **Basic**: Development and learning scenarios
- **Standard**: Production workloads with more storage and throughput
- **Premium**: Enterprise deployments with geo-replication, private endpoints, and content trust
- **Note**: Developer workflows work identically across tiers, but content trust and private endpoints require Premium

## Registry hierarchy
### Registry
- Top-level resource hosting all container content.
- Unique login server URL: <registry-name>.azurecr.io.
- Contains multiple repositories with authentication, access control, and management.
- Configure push/pull access, retention policies, and geo-replication at registry level.

### Repository
- Collection of container images with same name but different tags.
  - Example: inference-api repository contains all versions of your inference API image.
- New versions with different tags appear in the same repository.
- Supports namespaces using forward slashes for organization.
  - Group related images logically:
    - production/inference-api for production-ready images
    - staging/inference-api for validation images
- Namespaces enable access control.
  - Grant teams permission to push only to their namespace while restricting production access.

### Artifact
- Actual container image or content stored in a repository.
- Has identifying tags, content layers, and a descriptive manifest.
- Includes Docker images, Helm charts, or any OCI-compliant content.

## Tags, layers, and manifests
### Tags
- Identify specific artifact versions within a repository.
- Format repository:tag provides human-readable reference.
  - Example: inference-api:v1.2.0 refers to version 1.2.0 of the inference API image.
- Docker uses latest by default when no tag is specified.
- Single artifact can have multiple tags.
  - Tag image as both inference-api:v1.2.0 and inference-api:stable to indicate stable release.
  - Both tags reference the same underlying image.
- Tags are mutable.
  - Pushing new image with existing tag moves the tag to reference the new image.
    - Useful for latest tags but problematic for production deployments requiring consistency.

### Layers
- Each layer corresponds to a Dockerfile instruction that modifies the filesystem.
  - Example: installing packages or copying files creates new layers.
- Layers are content-addressable, identified by content hash.
- ACR shares common layers across images, reducing storage costs and accelerating pulls.
- Multiple images sharing base layer (e.g., python:3.11) store only one copy in registry.
- Deduplication valuable for AI applications sharing common ML framework layers.

### Manifests
- Every artifact has a manifest listing its layers and configuration.
- Manifest identified by SHA-256 digest: sha256:abc123....
- Unlike tags, digests are immutable.
  - Image digest never changes after pushing.
  - Pulling by digest guarantees exact image retrieval, even with new images using same tag.
  - Immutability critical for production AI deployments requiring node consistency.

## Address artifacts for push and pull operations
### By tag
- Tag-based addressing uses format registry/repository:tag.
- Provides human-readable references easy to remember and use in deployment configurations.

#### Azure CLI
```bash
# Push an image with a tag
docker push myregistry.azurecr.io/inference-api:v1.2.0
```

- Tag-based addressing works well for development and automatic update scenarios.
- Tags can change, making deployments potentially non-reproducible.

### By digest
- Digest-based addressing uses format registry/repository@sha256:hash.
- Guarantees reference to specific, immutable image regardless of tag changes.

#### Azure CLI
```bash
# Pull an image by digest
docker pull myregistry.azurecr.io/inference-api@sha256:0a2e01852872580b2c2fea9380ff8d7b637d3928783c55beb3f21a6e58d5d108
```

- **When to use**: Pull by digest for guaranteed reproducibility.
- **Production deployments**: Use digests where node consistency is critical.
- **Finding digests**: Available in Azure portal, Azure CLI, or push output.

## Best practices for organizing registries
- **Use namespaces**: Organize repositories by team, environment, or project using forward-slash notation.
  - Simplifies access control and image discovery.
- **Plan repository structure**: Group related images logically.
  - Group by deployment patterns, team ownership, or lifecycle needs.
- **Enable geo-replication**: For global AI deployments, replicate images to service regions.
  - Reduces pull latency and improves deployment reliability.
- **Monitor storage**: Track storage consumption and implement retention policies to remove untagged manifests.
  - Cleanup policies prevent unnecessary storage costs from accumulated images.
